
1. 对话持久化（最优先）
方案一：SQLite + LangGraph Checkpointer（推荐）


2. 多轮对话记忆 & 上下文窗口管理
当前项目是单轮——每次查询独立，不记住之前聊了什么。扩展方向：


用户: "紫金矿业怎么样"
AI:   [回答...]
用户: "那铜价呢"            ← 当前系统不理解"那"指代什么
实现：

短期记忆：将最近 3 轮对话摘要注入 system_prompt，让 Agent 理解上下文
长期记忆：将用户历史关注行业/股票做画像，下次主动推荐相关研报
滑动窗口 + 摘要压缩：用 LLM 把旧消息压缩成一段摘要，保持 context 窗口不过载


3. RAG 效果量化评估（RAGAS）
当前靠人工抽检判断回答质量。可以引入 RAGAS 框架做自动化评估：

以下是完整的 RAG 实现步骤。

RAG 整体架构

用户提问 → Agent 调用工具 → RagSummarizeService.summarize()
                              ├── 1. query_rewriter.rewrite()      查询改写
                              ├── 2. retrieve_docs()               多路检索
                              │       └── _retrieve() × N 个子查询
                              │           ├── hybrid_search()       混合检索
                              │           └── reranker.rerank()     重排序
                              ├── 3. context_assembler.assemble()  上下文组装
                              └── 4. chain.invoke()                LLM 总结
Phase 0：知识库构建（离线） — vector_store.py

data/*.txt, data/*.pdf
  │
  ├── 1. 扫描文件 (listdir_with_allowed_type)
  ├── 2. MD5 去重：已加载过的文件跳过
  ├── 3. 文档加载：txt_loader() / pdf_loader()
  ├── 4. 注入来源元数据 (source: 文件名)
  ├── 5. RecursiveCharacterTextSplitter 分片
  │      chunk_size=200, overlap=20
  │      分隔符: \n\n → 。→ . → ? → ？→ ! → 空格
  ├── 6. DashScopeEmbeddings (text-embedding-v4) 向量化
  ├── 7. 存入 ChromaDB
  └── 8. 重建 BM25 索引
关键配置（chroma.yaml）：



参数	值	作用
chunk_size	200	中文短分片，避免噪声
chunk_overlap	20	防止关键信息被切断
k	3	默认返回 top-3
Phase 1：查询改写 — query_rewriter.py
解决问题：用户输入是口语化的，不适合直接做向量检索。


用户: "紫金矿业最近涨得怎么样"
         │
         ▼
  QueryRewriter.rewrite()
  提示词模板 (query_rewrite.txt):
    - 口语→专业术语 ("涨价"→"价格上涨")
    - 补全时间信息 ("最新"→"2025/2026")
    - 拆分复合问题为 2-3 个独立检索词
    - 股票问题增加行业/产业链维度
         │
         ▼
  输出: [ "紫金矿业 2025年 股价走势 业绩分析",
          "黄金 铜 有色金属 行业景气度",
          "紫金矿业 产业链 竞争格局" ]
技术细节：

用 chat_model.invoke() 调用 LLM 做改写，不是规则匹配
LRU 缓存（128条），热点查询不改写第二次
改写失败时兜底返回原始查询
Phase 2：混合检索 — vector_store.py → hybrid_search()
每个改写后的子查询都会独立走这个流程。核心思想：向量检索 + 关键词检索 → RRF 融合，互补长短。

2a. 向量检索（语义相似度）

ChromaDB.as_retriever(k = k*2)    取 top-2k 候选
  │
  └── 基于 DashScope text-embedding-v4 的余弦相似度
      优势：理解语义，"涨价"能匹配到"价格上行"
2b. BM25 关键词检索

BM25Retriever.search(query, k*2)  取 top-2k 候选
  │
  └── 基于词频-逆文档频率的精确匹配
      优势：专业术语、股票代码等精确匹配
      BM25 索引在文档加载/删除时重建
2c. RRF 融合（Reciprocal Rank Fusion）

rrf_fusion(vector_results, bm25_results, k=3, rrf_k=60)
公式: score(doc) = Σ 1/(60 + rank_i + 1)
      对每个来源分别算排名分，加和，再排序取 top-k
优势：不依赖原始分数的绝对数值，只关心相对排名
Phase 3：重排序 — reranker.py → LLMReranker.rerank()
混合检索返回的结果是粗排的，重排序做精细筛选。  BGE-Reranker-v2-m3/Qwen3-Reranker

3a. Jaccard 去重

比较前 200 字符的字符集交集/并集
相似度 > 0.7 → 判定为重复 → 保留第一个
3b. 启发式评分

score(doc) =
  + 2.0    标题/首句包含查询关键词
  + 0.5×N  正文中关键词出现次数
  + 1.0    长度适中 (100-500 字符)
  - 1.0    过短 (< 20 字符)
按分数降序 → 取 top_k（默认 3）
Phase 4：多查询融合 — retrieve_docs()

对改写后的每个子查询:
  ├── _retrieve(sub_query): hybrid_search + rerank
  └── 合并结果，按内容前100字符去重
好处：比如"紫金矿业股价"和"铜价走势"两个子查询，分别拉回不同维度的资料，拼在一起更全面。

Phase 5：上下文组装 — context_assembler.py
把检索到的文档片段组装成 LLM 能消费的格式，核心是 Token 预算控制。


1. _group_by_source():    按来源文件名分组
2. _sort_groups():        按与查询相关性排序组
3. max_tokens=3000:       逐组填充，超出截断，打 "..." 标记
4. 格式化为:
   --- 文档1：紫金矿业深度报告.pdf ---
   紫金矿业2025年营收...
   --- 文档2：有色金属行业周报.pdf ---
   铜价受全球供给影响...
Phase 6：LLM 生成总结 — rag_summarize.txt

chain = PromptTemplate(template=rag_summarize.txt) | chat_model | StrOutputParser()
chain.invoke({"input": query, "context": assembled_context})
提示词约束（prompts/rag_summarize.txt）：

完全基于参考资料，不编造数据
开头不复述问题，直接进入分析
正文不嵌入式标注来源，末尾统一附引用清单
参考资料无相关内容时明确告知用户
整体数据流小结

用户: "紫金矿业最近怎么样"
 Phase 1 → ["紫金矿业 2025年 股价走势", "黄金铜矿 行业景气", "紫金矿业 产业链"]
 Phase 2 → 每个子查询: 向量检索 ∩ BM25 → RRF融合 → top-3
 Phase 3 → Jaccard去重 + 启发式评分 → 精选 top-3
 Phase 4 → 多查询结果合并去重 → 约 5-8 个文档片段
 Phase 5 → 按来源分组 + Token预算(3000) → 结构化上下文字符串
 Phase 6 → Prompt模板填入 {query} + {context} → LLM → 返回用户





 6. 定时任务与多渠道通知系统
APScheduler + YAML 配置驱动：agent/scheduler.py 基于 BackgroundScheduler（Asia/Shanghai 时区），从 config/scheduler.yaml 加载任务定义，支持 rag（研报生成）和 news（快讯摘要）两种任务类型
三通道推送：agent/notifier.py 实现了 EmailNotifier（SMTP+SSL，HTML 富文本）、DingTalkNotifier（钉钉机器人 Markdown）、FeishuNotifier（飞书交互式卡片消息），支持多通道同时推送
预设任务：交易日早盘综述、周五行业周报、盘中快讯摘要（9am/3pm）
7. 多策略 PDF 解析与并行处理管线
4 种解析策略：utils/file_handler.py 提供 PyPDF 基础提取、Unstructured hi_res（yolox_quantized 量化模型提速 + 表格/图片元素分离）、fast 模式（chi_sim 中文优化）、原生 partition_pdf 直调
多进程并行：ProcessPoolExecutor 并行解析 PDF（utils/parallel_pdf_loader.py），支持 tqdm 进度条
MD5 去重 + 双向一致性校验：rag/vector_store.py 的 load_document2() 在 ChromaDB 和 MD5 存储之间做双向一致性检查，任一方向数据缺失都能自动修复
元素分类保留：get_file_documents() 将解析结果分类为 texts、tables（保留 HTML 格式）、images，表格数据不丢失
8. 金融领域专项优化
交易所前缀自动识别：agent/tools/agent_tools.py 中 stock_quote_realtime() 自动判断 6xxxxx → sh（上证）、其余 → sz（深证），匹配新浪财经 API 规范
金融术语合规校验：agent/tools/middleware.py 的 QualityGuard 禁止输出中出现「暴涨」「暴跌」「保证收益」「稳赚」「必涨」「必跌」等不合规表述
股票代码强制匹配：rag/rag_service.py 的 _check_context_relevance() 要求查询中的 6 位股票代码必须在检索上下文中精确命中，否则判定检索失败
9. 分层容错与优雅降级
Query Rewrite 降级：LLM 改写失败时自动回退为原始单条查询
上下文 N-gram 相关性校验：检索结果与查询的 N-gram 重叠度检测（rag/rag_service.py），自动过滤无词汇重叠的文档，保证至少 1 条文档幸存
7 种流式错误分类诊断：额度耗尽、403 禁止、401 未授权、超时、通用错误等，每种都提供中文诊断提示
ModelCallLimit(10) / ToolCallLimit(5)：防止 Agent 陷入无限循环
10. 全链路可观测与评估体系
引用累积追踪：agent/tools/middleware.py 的 CitationTracker 跨多轮工具调用累积 【来源:...】 引用，供前端可视化展示
LangSmith 全链路追踪：所有 LangGraph 运行自动上报 LangSmith
RAGAS 中文适配评估：evaluation/eval_runner.py 将 RAGAS 4 项指标的 Prompt 示例自动翻译为中文，内置 12 题金融 Q&A 测试集（覆盖紫金矿业、茅台、阳光电源等），当前评估结果：faithfulness 0.67、answer_relevancy 0.74、context_recall 0.50
结构化日志：utils/logger_handler.py 双输出（控制台 INFO + 每日 DEBUG 日志文件），全模块统一 [ComponentName] 前缀规范
11. 前端体验优化
品牌化 UI：app.py 中包含约 300 行自定义 CSS，定义了蓝金配色、卡片式布局、聊天气泡、引用块样式、脉冲动画停止按钮
流式对话 + 实时取消：daemon 线程执行 Agent，主线程 0.5s 轮询刷新，停止按钮立即中断并标记 [已中断]
示例查询按钮：4 个预设快捷入口（分析紫金矿业、有色金属展望、茅台近期走势、生成阳光电源研报）
对话导出：当前会话导出为 TXT 文件，含时间戳和角色前缀
数据库浏览器：viewer.py 独立 Streamlit 应用，可浏览 ChromaDB 集合内容
12. 工程化实践
配置/密钥分离：config/*.yaml 存结构配置，.env 存密钥（已 gitignore）
Streamlit Secrets 降级：model/factory.py 先读环境变量，读不到再读 st.secrets

模块级自测：vector_store.py、rag_service.py、react_agent.py、prompt_loader.py 均在 __main__ 中内嵌可执行测试用例
